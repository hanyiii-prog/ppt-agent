# V3.1 Aesthetic Convergence

V3.1 connects model intent to template-aware PPTX execution. It does not ask the model to draw;
it asks the model to choose structure, then validates that structure against source evidence,
template capacity and rendered page gates.

## Generation contract

```text
Markdown / source
  ↓
storyboard/v1 + JSON schema
  ↓
validate + alias normalisation + row windows
  ↓
template-component-catalog/v1
  ↓
clone page plan: role, kit, template_component_id, table_row_ranges
  ↓
template slide reuse or native page kit
  ↓
render ALL pages
  ↓
page gate + visual review + editability + template fidelity
  ↓
single-page repair → rebuild → whole-deck gate
```

The model may select titles, key messages, archetypes, layout variants, visual kits and optional
template components. It may not invent facts, omit source blocks without a reason, or bypass the
page plan validator.

## Provider selection

`resolve_provider()` uses this order:

1. **Host MCP sampling** when the host declared `sampling` in `initialize`.
2. **Configured fallback models** when `PPT_AGENT_FALLBACK_API_BASE_URL`,
   `PPT_AGENT_FALLBACK_API_KEY` and `PPT_AGENT_FALLBACK_MODELS` are present.
3. **Direct Responses provider** when no host sampling session exists and
   `PPT_AGENT_API_BASE_URL`, `PPT_AGENT_API_KEY` and `PPT_AGENT_MODEL` are complete.

The report records `generation_provider` and `generation_model`. Direct configuration is a
compatibility path, not an override of the host model.

## Storyboard

`storyboard/v1` is validated by JSON schema and normalised before rendering:

- unsupported `visual_kit` values are aliased (`metrics_row` → `quad_cards`,
  `timeline` → `progress_timeline`, and so on);
- unknown layout variants degrade to `standard`;
- unsupported kits become an automatic layout choice with a warning instead of discarding the
  whole storyboard;
- source blocks must be used or explicitly omitted;
- table pages can use 1-based `table_row_ranges`, preventing a 30-row source table from being
  crammed onto one slide.

Current supported kits include `quad_cards`, `column_cards`, `two_panel_list`, `stage_cards`,
`progress_timeline`, `stage_timeline`, `matrix_table`, `architecture_layers`, `four_role_cards`
and `org_chart`.

## Template component catalog

`template-component-catalog/v1` catalogues every template page, not only repeated chrome. Each
entry records the source slide, page kind, semantic component kind, tags, slot count, item/text
capacity, table count and writable slot inventory.

The renderer prefers a template slide when a catalog match exists. It assigns the source slide
with `cleared=False`, writes text into template slots and keeps native shapes, images, gradients
and tables. If the plan cannot fit the component's text capacity, or no matching template component
exists, the build falls back to a `page_kits` route and reports the reason.

## Whole-deck gates

After the first build and after every repair iteration, PPT Agent re-renders and gates the whole
deck:

- page count and dimensions;
- bounds, zero-size shapes, collisions and overflow;
- near-blank detection;
- deterministic visual checks, plus model review only when a vision-capable model is explicitly
  available;
- template layout/master fidelity;
- native editability.

MCP callers should pass `params._meta.progressToken` to `ppt_agent_generate`. The server emits
`notifications/progress` for parse, analysis, storyboard, layout, render, gate and repair stages.
